# Building AI Systems in Public Without Lying to Yourself

**How public work became an evidence system for separating interfaces from products, executable metaphors from validated claims, attention from adoption, and speed from maturity.**

*Published December 1, 2025 · Updated July 2026*

---

# I can build faster than I can prove

I can build a convincing AI system faster than I can prove that the system deserves to exist.

That may be the central problem of modern AI engineering.

With current models, interface generators and deployment platforms, an idea can become something that looks like a product in hours. The landing page works. The dashboard looks complete. The architecture diagram is impressive. An agent produces one successful result. A public URL exists.

For a brief moment, builder, audience and system participate in the same illusion: visible completion feels like demonstrated capability.

I have done this repeatedly—not because I wanted to deceive anyone, but because creation moves faster than verification.

Ideas are not my scarce resource. I can imagine a governance operating system for agents, a middleware for the AI Act, an entropic stability layer, a human benchmark, a living vendor intelligence graph, a trace platform, a coffee recommendation engine and an interactive AI laboratory before breakfast.

The difficult question is not what I can imagine.

It is this:

> **Which part exists, which part works, which part is architecture, which part is a demonstration, and which part remains an ambitious hypothesis?**

Building in public is not my marketing strategy. It is my mechanism for separating invention from evidence.

# The speed of creation has become dangerous

AI has compressed the cost of producing evidence-shaped objects much faster than it has compressed the cost of producing evidence.

We can generate screenshots, benchmarks, reports, dashboards, architecture diagrams, synthetic traces and plausible percentages almost instantly. All of them look like proof. None of them proves more than its production process supports.

A generated dashboard proves that a dashboard can be designed. A synthetic benchmark proves that a program produced a result under defined synthetic conditions. A public deployment proves that an interface can be reached. A passing test proves that a particular assertion held in a particular environment.

Those are useful facts. They are not the same fact.

The visual distance between idea and product has collapsed. The operational distance remains:

- users;
- persistence;
- evaluation;
- resilience;
- security;
- observability;
- real costs;
- adversarial cases;
- maintenance;
- business outcomes.

This makes technical honesty a design problem. If the interface does not explain its evidence state, visitors will infer one from visual polish. Usually they infer too much.

# Interface reality is not execution reality

The most important redesign of my portfolio was not typography or animation. It was changing the labels under the previews.

Different artefacts now carry different evidence states:

| Evidence state | What it honestly proves |
|---|---|
| Real product interface | The public product surface exists and can be used |
| Real interface · Demo data | The interface is real; the visible dataset is illustrative |
| Real interface · Snapshot data | The interface is real; the data has a declared capture date |
| Representative workflow | The composition is based on the system but is not a live run |
| Concept visualization | The visual explains an idea rather than proving execution |
| Architecture diagram | The components and boundaries are a design claim |
| Recorded execution | A run happened previously under stated conditions |
| Live execution | The result is generated now from the operating system |
| Generated from package output | The visual derives from executable package output |
| Real anonymised trace | The trace is operational evidence with reviewed disclosure |

The labels initially felt like a downgrade. They were not.

They transformed visual ambiguity into technical honesty.

A representative workflow is not less valuable because it is representative. It becomes less valuable only when it pretends to be operational evidence. A concept visual can demonstrate systems thinking. A snapshot can demonstrate a data model. A real interface can demonstrate product craft. A trace can demonstrate actual execution.

The label protects the claim and helps the viewer interpret the skill correctly.

# The evidence ladder

Public work becomes useful when every project can move through explicit evidence states.

1. I had an idea.
2. I described an architecture.
3. I built an interface.
4. I implemented a prototype.
5. I executed it on synthetic data.
6. Someone else could run it.
7. The result was reproducible.
8. It survived an adversarial or failure test.
9. Somebody used it without me.
10. Somebody continued using it.
11. It created measurable value.
12. It remained operable over time.

Higher is not always necessary. A research prototype may achieve its purpose at step seven. A product claim should not borrow the language of step twelve while presenting evidence from step three.

For every public claim, I now want four attached fields:

- **Claim** — precise, scoped and falsifiable.
- **Proof** — URL, package, repository, trace, test or captured output.
- **Boundary** — demo data, synthetic environment, representative composition or conceptual layer.
- **Freshness** — date last verified and known degradation.

The evidence ladder is not a badge system. It is a mechanism for deciding what to build next. If the interface is strong but reproducibility is weak, another redesign is not progress. The next unit of work is a clean install, a fixture, a test and expected output.

# My portfolio needed a control plane

I eventually realised that my portfolio had the same problem as an ungoverned agent platform.

It contained many capable objects, but no shared system for declaring what each object was, which version was current, what it was authorised to claim, what evidence supported that claim, and whether it was active, experimental or abandoned.

My portfolio did not need another gallery.

It needed a control plane.

| Portfolio object | Governed-system equivalent |
|---|---|
| Project | Registered agent or service |
| Claim | Capability declaration |
| Status | Lifecycle state |
| Public demo | Execution surface |
| GitHub or PyPI | Inspectable evidence |
| Case study | System record |
| Preview label | Evidence classification |
| Changelog | Audit trail |
| Remove a claim | Permission revocation |
| New release | Governed version |

That parallel changed the architecture of the site. Projects stopped being equal cards in a horizontal gallery and became layers in a larger argument: governance, runtime, stability, safety, observability, intelligence and applied products.

The portfolio became a registry. Each system needed identity, state, evidence, limitations, links and last verification date.

This did more than improve presentation. It revealed what I had been building all along.

# The public record became an architectural mirror

AI Act Middleware, Entropic Core, PsycheOS, LLMTRACE and AI Vendor Compare initially looked like separate obsessions.

Publishing them forced comparison. The repeated concerns became visible:

- governability;
- observability;
- evidence;
- stability;
- orchestration;
- runtime control;
- cost;
- safe intervention.

I was not only building applications. I was building control layers around AI systems.

Building in public did not merely show other people what I was making. It showed me the architecture connecting work that had felt independent.

> **The public record became an architectural mirror.**

This is one of the highest-value forms of public feedback: not comments, stars or likes, but the pressure to explain several projects in one coherent model. If the model cannot explain them, the portfolio may be an archive of experiments rather than an argument about current capability.

# Downgrade the claim. Upgrade the experiment.

Entropic Core began with large metaphors: informational gravity, truth mass, probabilistic regulation, cognitive immune systems and entropy as a force in LLM workflows.

Metaphors can generate architecture. They are not measurements.

The honest path is:

```text
wild intuition
    ↓
executable metaphor
    ↓
synthetic experiment
    ↓
architectural mechanism
    ↓
testable hypothesis
    ↓
controlled benchmark
    ↓
production evidence
```

Building in public taught me that an executable idea is not yet a validated idea.

Code proves that a rule can be implemented. A simulation proves that programmed actors respond to that rule. Neither proves that the rule describes reality or improves a production system.

I did not have to abandon the metaphor.

I had to downgrade the claim and upgrade the experiment.

That principle is more ambitious than protecting an impressive sentence. A narrower claim that survives inspection can become a foundation. An enormous claim supported by a beautiful graph remains fragile.

# Negative results are public assets

A private experiment can fail silently. The builder removes the result, keeps the narrative and moves on. Public work creates pressure either to disguise the failure or convert it into knowledge.

The second option is more valuable.

A benchmark that refuses to confirm the landing page may be the best component of the system. It identifies an assumption that was doing hidden work. It can reveal that the evaluator is correlated with the generator, that the data is too easy, that a metric has no stable denominator, or that a control improves one failure mode while making another worse.

Some of my best architectural decisions began when a system refused to prove the story I wanted to tell about it.

A useful negative-result record contains:

- the hypothesis;
- the environment and versions;
- the expected signal;
- the actual result;
- plausible confounders;
- the claim that changed;
- the next experiment;
- the decision to continue, narrow or stop.

Failure becomes credible when it changes authority. If a benchmark fails, the corresponding claim loses permission to appear as established fact.

# Shipping creates entropy

The standard building-in-public narrative glorifies motion: ship every day, launch every week, publish everything.

Volume creates its own entropy.

When I build ten systems, versions diverge. Claims contradict each other. Domains fail. Documentation ages. Dependencies become vulnerable. Screenshots stop matching the application. Names stop expressing the architecture. Some projects evolve while others remain frozen in a portfolio that still presents them as current.

Shipping is not the opposite of unfinished work.

Shipping creates a new category of unfinished work: maintenance, evidence, documentation, versioning and narrative coherence.

That requires portfolio operations:

- a canonical project registry;
- lifecycle states;
- health checks for public URLs;
- package and repository verification;
- evidence review dates;
- changelogs;
- claim retirement;
- explicit archival decisions;
- hierarchy between flagship, foundation, experiment and applied product.

The cost of a new project is not its first deployment. It is the future attention required to keep its public meaning accurate.

# Not every project deserves the same stage

Every project contains time, obsession and a piece of identity. That makes it emotionally difficult to remove one from the home page.

But a portfolio is not an archive of everything I have made.

It is an argument about what I am capable of building now.

If twenty projects receive equal weight, breadth becomes noise. The viewer has to infer which systems are real, strategic, maintained and representative. Most will not invest that effort.

Removing a project from the home page does not erase the work. It restores hierarchy.

The strongest public system should lead. Foundational components should support it. Experiments should remain discoverable with explicit maturity. Applied products should demonstrate range without obscuring the central thesis.

Good curation is a technical claim about relevance.

# Feedback is telemetry, not truth

Attention is a noisy sensor.

Many likes do not prove product-market fit, safety, architecture quality or scientific validity. Few likes do not disprove any of them. Public response is still useful when interpreted at the right level.

It can reveal:

- what people cannot understand;
- which claim creates doubt;
- where a workflow breaks;
- which use case produces curiosity;
- which language sounds synthetic;
- where evidence is missing;
- what someone tries to verify next.

Attention is a signal. Adoption is evidence. Reproducibility is stronger evidence. Continued use is stronger still.

I want feedback connected to an observed task: a failed install, a misunderstood preview, a missing source, a repeated question, a workflow someone completes, or a decision they can make with the product.

Generic praise feels good and changes little. A specific objection can improve the architecture.

# Open source is a contract, not a medal

Publishing code does not make unfinished software finished. It makes unfinished software externally inspectable.

That creates obligations:

- correct package metadata;
- reproducible installation;
- versioned APIs;
- examples and expected output;
- tests;
- licensing;
- security review;
- documented limitations;
- honest maturity;
- response to breakage.

A package with placeholder authorship, unexplained compatibility or an impressive README that cannot be reproduced may reduce trust more than it creates.

Publishing a package is not the end of development. It is the moment internal assumptions become somebody else's dependency.

LLMTRACE is useful portfolio evidence because a visitor can move beyond the interface: inspect the repository, install a release and understand the trace model. That proof path is stronger than a screenshot, even if the package remains early and scoped.

# Transparency without threat modelling is leakage

Public evidence can expose more than intended.

Prompts may contain customer data. Screenshots may reveal email addresses, API keys or internal endpoints. Traces may identify users through combinations of fields even after names are removed. Git history may retain secrets after the visible file is cleaned.

Building in public requires a disclosure architecture:

1. Classify the artefact.
2. Remove secrets and direct identifiers.
3. Test combinations that could re-identify a person or organisation.
4. Separate operational metadata from restricted content.
5. Use synthetic data when the real data is not required for the claim.
6. State when a trace is anonymised, representative or recorded.
7. Review the final rendered surface, not only the source file.

Evidence must be public enough to inspect and constrained enough to avoid exposing users, organisations or infrastructure.

Transparency without threat modelling is not openness. It is leakage.

# The uncomfortable admission

I have published systems before their claims were properly calibrated.

I have mistaken passing tests for production readiness.

I have allowed generated interfaces to imply more operational maturity than the underlying system could demonstrate.

I have used ambitious metaphors before designing the experiment required to defend them.

And I have built faster than I could maintain the evidence around what I had built.

Building in public did not prevent those mistakes.

It made them visible enough to correct.

That is the difference between public performance and a public evidence system. Performance rewards certainty. Evidence permits revision.

# A public evidence lifecycle

I now treat publication as a governed lifecycle.

## Before publishing

- What exactly exists?
- What executes live?
- Which data is real, synthetic, demo or snapshot?
- What claim is being made?
- Which artefact proves it?
- Can another person reproduce the result?
- What remains untested?
- Which limitation changes interpretation?
- What could expose a secret, user or organisation?
- Who owns maintenance after launch?

## At publication

- Label the preview state.
- Link the strongest evidence directly.
- Record version and verification date.
- State the evidence boundary near the claim.
- Provide a minimal first-run path.
- Publish expected output and failure behaviour.
- Add a changelog entry.

## After publishing

- Which link or workflow failed?
- What did visitors misunderstand?
- Which claim generated legitimate doubt?
- Did anyone reproduce the proof?
- Which metric needs a baseline?
- Which dependency or dataset aged?
- Does the project deserve continued maintenance?
- Should the claim be upgraded, narrowed or retired?

The record should be able to disagree with the builder. Otherwise it is marketing content with timestamps.

# A concrete portfolio evidence map

The systems in this portfolio now demonstrate different kinds of proof.

## BrewMatch

The public product interface demonstrates product design, structured preference capture and a real discovery surface. It should not imply ownership of merchant inventory, checkout or fulfilment.

## AI Vendor Compare

The interface is real and the visible vendor data is a time-stamped snapshot. The architecture for continuous claim discovery and verification is a target operating model, not a hidden claim that every price is already updated live each day.

## AI Act Middleware

The public prototype demonstrates a governance surface and control-plane concepts. It does not certify compliance automatically.

## Entropic Core

Package and laboratory output demonstrate an executable control-loop hypothesis. Synthetic dynamics do not prove universal scientific laws or production efficacy.

## LLMTRACE

The repository, package and anonymised trace provide inspectable evidence of an observability implementation. They do not by themselves prove enterprise-scale operations.

This variety is a strength when the states are explicit. The portfolio no longer forces every project into the same preview category.

# What I measure now

Public-building metrics should describe evidence movement, not only distribution.

| Metric | What it asks | Failure signal |
|---|---|---|
| Proof conversion | Does a visitor reach the runnable or inspectable artefact? | Claims attract attention but evidence is never opened |
| Reproduction success | Can another person obtain the expected result? | Setup depends on hidden local knowledge |
| Evidence freshness | Are URL, package, screenshot and claim still current? | Polished previews point to degraded systems |
| Boundary clarity | Can viewers distinguish interface, data and execution state? | Repeated questions imply inflated interpretation |
| Learning closure | Did feedback change a decision, test or release? | Public response produces activity without learning |
| Maintenance burden | What does the public record cost to keep true? | New launches outpace verification capacity |

The metrics are not universal. They force me to decide what publication is meant to accomplish.

# What I would do differently

I would establish the evidence state before designing the preview.

I would build the smallest reproducible proof before adding another dashboard panel.

I would give each project one lead claim and one obvious verification path.

I would version policy, data and prompts from the first release.

I would publish fewer projects on the main stage and maintain a deeper experimental archive.

I would treat negative results as first-class content earlier.

I would define retirement criteria at launch.

And I would ask a harder question before every ambitious phrase: what experiment would have to succeed for this sentence to become true?

# Build in public, but govern the public record

I used to think building in public meant showing people what I was creating.

I now think it means creating a public record strong enough to disagree with me.

A record that tells me when a product is only an interface. When an experiment is only a simulation. When a metric is only a placeholder. When a framework is still a hypothesis. When a collection of projects has finally become an architecture.

The greatest value of building in public has not been visibility.

It has been resistance.

Resistance against exaggerated claims. Resistance against private perfection. Resistance against the temptation to confuse speed with maturity.

I still build quickly. I still follow ideas further than is probably reasonable. I still believe that some valuable systems begin as ideas that initially sound excessive.

But now I ask each idea to leave evidence behind.

Because a private idea can remain extraordinary forever.

A public system has to survive contact with reality.
